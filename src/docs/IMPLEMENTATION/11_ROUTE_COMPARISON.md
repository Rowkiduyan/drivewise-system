# Phase 11 - Route Comparison (Suggested vs. Actual)

## Goal

Wire up "suggested route vs. actual route driven" for a completed Trip: the route generated before the Trip started, overlaid against the real path reconstructed from GPS, so a Supervisor can see how far the driver deviated. Per `00_IMPLEMENTATION_RULES.md`'s Existing UI rule, this connects real data into UI that already exists (see "What's already built" below) rather than designing a new screen.

Requested alongside two adjacent questions, both addressed here: whether the comparison should render as two differently-colored trails (yes — see "Rendering"), and whether traffic/roadwork data can inform the suggested route (see "Traffic-Aware Suggested Routes").

## What's already built

- **`01_SYSTEM_ARCHITECTURE.md`'s "Route Comparison" section** already defines the concept: "The suggested route belongs to the Trip. The actual route is reconstructed by combining the GPS logs from all Sessions belonging to that Trip, in chronological order." `05_GPS_PIPELINE.md` and `DATABASE.md`'s `gps_logs` entry both already build toward this — the `(session_id, timestamp)` index exists specifically to support it.
- **`SupDeliveries.jsx` already has the comparison UI**, fully built, currently mock-only: `RouteDeviationMap` (`:1057`) renders a Leaflet map with two `Polyline`s — planned route as a green dashed line (`#059669`, `dashArray: '8 6'`), actual route as a blue solid line at 70% opacity (`#2563eb`) — plus start/end markers. This is the "opposite color trail" already implemented; it just needs real data instead of `completed_delivery_reports`' mock `planned`/`actual` arrays (`:1730`). It's shown as the "Route Deviation Report" tab (`REPORT_TABS`, `:994`) inside a Completed Delivery's report view — but only for the handful of mock delivery ids that happen to have a matching `completed_delivery_reports` entry (`02C_ROUTE_STYLING_AND_PROOF_VISIBILITY.md`'s Supervisor section already flagged this: "Real DB-backed deliveries fall back to just Details + Quotation").
- **The actual route's data source already works**: `gps_logs` (`delivery_request_id`, `session_id`, `latitude`, `longitude`, `timestamp`) is populated live by Phase 5, and is already `authenticated`-readable (grant added 2026-08-12 for `LiveNavigationMap`).

## What's missing

~~**The suggested route is never persisted.**~~ Resolved 2026-08-14 — see "Deliverable" below. Left as-written for the historical context of what motivated this doc originally: `02_BOOKING_AND_TRIP_CREATION.md` (gap #1, still open) planned a stored route column on `delivery_requests`, generated once at trip-creation time via the Routes API. That never got built. What actually shipped instead (`DriverDeliveries.jsx`'s `LiveNavigationMap`, `01_SYSTEM_ARCHITECTURE.md`'s Route Comparison section, 2026-08-12) is a client-side `DirectionsService` call, recomputed live every time the driving stage renders, and — critically — its pickup-leg `origin` is `livePosition || origin` (`DriverDeliveries.jsx:497`), i.e. it starts from wherever the driver currently is, not a fixed pre-trip point. That's correct for turn-by-turn navigation (re-route around the driver's real position) but means there is currently no single, fixed "the route we suggested for this Trip" artifact to compare against after the fact — it was different on every recompute.

## Required Schema

Per `00_IMPLEMENTATION_RULES.md`, this needs a new column before any of this can be built — reported here, not assumed:

- `delivery_requests.suggested_route` (jsonb, nullable) — the frozen suggested route for the whole Pickup → Dropoff → Stops chain, generated once and never recomputed. Shape: an array of per-leg entries mirroring the existing `stops` jsonb convention, e.g. `[{"from": "pickup", "to": "dropoff", "path": [[lat,lng], ...]}, {"from": "dropoff", "to": "stop_1", "path": [...]}, ...]` — one entry per `DirectionsService` leg, each `path` taken from that leg's own points (Google's `overview_path`, or the denser per-step `lat_lngs` if finer resolution is wanted — see `scripts/fixtures/DR-0020-legs.json`, already captured this way for `02C`'s test tooling, as a working precedent for "every point along the actual road-following path, not just each turn's end point").

No other schema is missing — `gps_logs` already carries everything needed to reconstruct the actual route.

## Design

### Capturing the suggested route

`PlannedRouteMap` (`DriverDeliveries.jsx`) calls `DirectionsService` once with `WAREHOUSE_ADDRESS` as origin, followed by the nearest-ordered Pickup→Dropoffs→Stops waypoint chain, the first time it renders for a delivery with no `suggestedRoute` already saved (checked client-side via the `admin-users`' `get-driver-deliveries` response, and again server-side in `driver-trip`'s `save-suggested-route` action, which silently no-ops a second write instead of overwriting). Each leg's dense per-step `path` (not `overview_path`) is persisted into `suggested_route` via that action — a one-time write, not a subscription; the component renders the saved route directly (no fresh `DirectionsService` call) on every subsequent view once it exists.

### Reconstructing the actual route

Exactly as `01_SYSTEM_ARCHITECTURE.md` already specifies: query `gps_logs` for the Trip's `delivery_request_id`, ordered by `timestamp`, and concatenate — a Trip spanning multiple Sessions (Pause/Resume) combines all of them in order, per `05_GPS_PIPELINE.md`. Only `session_id`-attributed readings count (Active-Session rows) — Paused-Trip readings (`session_id is null`) are for the Supervisor's live-position/anomaly view (`08_REALTIME_DASHBOARD.md`'s Paused-movement banner), not route reconstruction, matching the distinction that doc already draws.

### Rendering

`RouteDeviationMap` (`SupDeliveries.jsx`) now takes `plannedLegs` (array of `{path, color}`, one per leg of `suggested_route`, colored via a local `NAV_LEG_COLORS`-matching const so the comparison view uses the same per-leg color language `LiveNavigationMap` already does) instead of a single flat `plannedRoute` — extended from the single-leg shape described above. `actualRoute` stays one continuous solid-blue polyline (no leg-splitting; there's no reliable per-leg arrival timestamp to split the real GPS trace on).

Fed by `buildRealTripAndBehaviorReport`'s new `routeDeviation` field (real `delivery_requests.suggested_route` + the same `gps_logs` reconstruction that function already does for its other tabs) when a delivery has a saved `suggested_route`; `RouteDeviationTab` normalizes both that real shape and the legacy `completed_delivery_reports` mock's flat `planned`/`actual` fixture shape into what `RouteDeviationMap` expects, so both keep working. A delivery with no saved `suggested_route` (predates this feature, or its trip was never actually driven far enough to view the pre-trip screen) simply doesn't get the "Route Deviation Report" tab at all — same "real data if present, otherwise say so" precedent as this file's `ProofOfDeliverySection`/DriveWise Alerts, not a fabricated fallback. No AI narrative/deviation-segments/schedule-impact/fuel-impact fields are invented for the real path either (those stay legacy-mock-only, guarded off) — no real analysis pipeline produces them.

## Traffic-Aware Suggested Routes

Separate question, same area: yes, this is available, at two different levels —

- **Departure-time traffic prediction** (cheapest, no separate API): `DirectionsService`'s request already supports `drivingOptions: { departureTime: new Date(), trafficModel: 'bestguess' | 'pessimistic' | 'optimistic' }` — this shifts the *suggested* route's timing/routing decision based on predicted traffic at departure time, and the response's `duration_in_traffic` field gives a traffic-aware ETA. This directly makes "the suggested route makes sense" — no new API needs enabling, since `DirectionsService` is already in use; just add `drivingOptions` to the existing `computeRoute` call (`DriverDeliveries.jsx:456`) and to whichever call ends up generating `suggested_route` above.
- **Live traffic/incident overlay** (visual only, no routing effect): Google Maps JS API's `TrafficLayer` renders live congestion coloring directly on a `google.maps.Map` instance. **Built 2026-08-30** (reversing the 2026-08-13 decision to skip it, logged in `STATUS.md`) — `<TrafficLayer />` now renders inside `LiveNavigationMap`'s `<GoogleMap>` (`DriverDeliveries.jsx`), so the driver can see congestion, not just get routed around it. This does **not** cover closures/roadwork/accidents as discrete labeled incidents — Google doesn't expose an incidents API to third parties; `TrafficLayer` only shows speed-based congestion coloring. Actual road closures are already handled indirectly: `DirectionsService`'s normal routing already avoids a road it knows is closed, and the existing rerouting-on-deviation logic (`DriverDeliveries.jsx`, `isLocationOnEdge`) already reacts if the driver has to detour around one live.

Both are additive to the existing `DirectionsService`/`@react-google-maps/api` stack already paid for and enabled (`02_BOOKING_AND_TRIP_CREATION.md`'s Google Maps Platform Setup) — no new billing category, just request parameters and one more rendered layer.

## Reroute-Aware Deviation Verdict

**Built 2026-09-11, live-verified end-to-end against the real Supabase project** (simulated GPS movement on a real assigned delivery, confirmed the reroute fired silently with no UI interruption, confirmed the `reroute_events` row landed, confirmed the tagging widget and the persisted reason on a real completed trip). The reroute-on-deviation logic above (`isLocationOnEdge`, ~100m tolerance, unmodified from its original tuning) itself is unchanged — it's still fully automatic, no driver interaction, no button, nothing mid-drive, per explicit user decision that the customer-booked `suggested_route` stays the trip's authoritative plan and a driver should never need to fiddle with the phone while actually driving. What changed: every time it fires, the resulting path is now persisted to a new `reroute_events` table (`DATABASE.md`), via a new `driver-trip` action `log-reroute` — fire-and-forget with one silent retry on failure (checking `invoke()`'s resolved `{error}`, not just a rejected promise, since a non-2xx response resolves rather than rejects), never blocking or surfacing an error into live navigation. `log-reroute` validates `newPath` is actually an array of finite `[lat,lng]` pairs server-side (mirrors `log-position`'s own `Number.isFinite` guard) — a malformed point would otherwise insert silently and then just never match anything in the distance math below, quietly defeating the whole feature.

`classifyRouteDeviation` (`lib/suggestedRoute.js`) gained an optional `rerouteSegments` param — `[{ path, occurredAt }, ...]`. A GPS point close to any of these logged app-initiated paths now correctly reads as on-route rather than counting against the driver as unexplained deviation, but only for points recorded at or after that reroute's own `occurredAt` — a reroute can't retroactively excuse an excursion the driver made before the app had even computed that path yet (otherwise a genuine, unrelated deviation that happens to pass near a *later* reroute's route would get incorrectly laundered as legitimate). A shared `fetchRerouteEvents(deliveryRequestId)` helper (`lib/suggestedRoute.js`) and `flattenLegPath(leg)` (the same per-step-path unwrapping `computeSuggestedRoute` already did, now shared with `log-reroute`'s path-building) keep this from being three copies of the same query/logic — `buildRealDriverTripReport` (`DriverDeliveries.jsx`), its shared reuse in `HelperDeliveries.jsx` (imports the same function/component, not a duplicate — see that file's own convention), and `buildRealTripAndBehaviorReport` (`SupDeliveries.jsx`) all call it, so Driver, Helper, and Supervisor see the same corrected verdict for the same trip. `reroute_events` are surfaced as a **top-level `rerouteEvents` field** on the report object, independent of whether a `routeDeviation` comparison could be built at all — a delivery with logged reroutes but no saved `suggested_route` (rare, but `LiveNavigationMap` still navigates/reroutes either way) still gets to show and tag them, it just doesn't get the map/distance-verdict part.

A reason (`road_closed`/`accident`/`wrong_turn`/`other`, fixed presets, no free text) can optionally be attached to a reroute afterward — never as a live-driving prompt, only from the Driver reviewing their own completed trip's report (`CompletedDeliveryReport`'s "Route changes on this trip" widget, via a new `tag-reroute-reason` action, one PostgREST embedded-join query for the ownership check rather than two sequential ones). Skippable entirely; an untagged reroute is still correctly excluded from the verdict, the reason is purely supplementary color for the Driver's own records. The Supervisor's and Helper's views show any given reason read-only (`canTagRerouteReason` prop gates the tap targets off for Helper, since only the Driver's own `assigned_driver_id` passes `tag-reroute-reason`'s ownership check) — only the Driver can tag it.

New table `reroute_events` needed its own follow-up migration the same day (`20260911130000_reroute_events_revoke_defaults.sql`) — `SUPABASE_GOTCHAS.md` #8's "new tables auto-inherit anon/authenticated baseline grants" gap, caught in review rather than by a later Advisor audit this time; RLS had been denying it in the meantime, but the explicit `revoke all ... from anon, authenticated` was added to close it properly rather than relying on RLS alone. Also fixed in review, before either migration/deploy: the "Planned — Leg N" labels in both `RouteDeviationMap` legends (Driver and Supervisor) were renamed to "Planned — Route N" (user-facing copy only, internal `legs`/`plannedLegs`/`NAV_LEG_COLORS` naming untouched — renaming those too would collide with this feature's own already-overloaded "route" vocabulary).
