## 1. `SECURITY DEFINER` functions with mutable `search_path`

Flagged: `current_user_role`, `is_admin`, `is_supervisor`, `set_driver_records_updated_at`, `enforce_role_change_admin_only`, `enforce_supervisor_status_only_update`, `rls_auto_enable`, `delivery_request_visible_to_caller`, `session_visible_to_caller`, `specialized_crew_available_days`.

**Resolved 2026-08-30** — the contradiction between `SUPABASE_GOTCHAS.md` gotcha #9 (says `search_path` is already set) and the Advisor (said mutable) was settled by reading every flagged function's live definition directly (`pg_get_functiondef`/`pg_proc.proconfig`), not trusting either source. Result: **8 of the 10 already had `search_path` correctly set** — `current_user_role`, `is_admin`, `delivery_request_visible_to_caller`, `session_visible_to_caller`, `enforce_role_change_admin_only`, `enforce_supervisor_status_only_update`, and `specialized_crew_available_days` all show `search_path=public`; `rls_auto_enable` shows `search_path=pg_catalog` (correct and deliberate — see §2 below). `SUPABASE_GOTCHAS.md` was accurate; the Advisor export this doc started from was simply stale by the time it was checked.

Only **`is_supervisor`** and **`set_driver_records_updated_at`** genuinely had no `search_path` set — and neither is `SECURITY DEFINER` (`prosecdef = false` for both), so the actual exploit path this lint warns about (a hijacked search_path escalating to the function owner's privileges) doesn't apply to either — they run with the caller's own privileges. `set_driver_records_updated_at` was fixed anyway as harmless hygiene: `alter function public.set_driver_records_updated_at() set search_path = public;`, verified via `pg_proc.proconfig` afterward. `is_supervisor` was **not** touched — see the new finding below instead.

**`is_supervisor()` — resolved 2026-08-30, dropped.** Initially suspected dead from a repo grep alone (no migration, no Edge Function, no live table-RLS policy referenced it). That grep was incomplete: `DROP FUNCTION` failed with a real dependency error — two `storage.objects` policies (`Supervisors can update/delete driver profile pictures`) were gated on it, neither visible to a `src/`/`supabase/` grep since they were created directly in the Supabase dashboard (same ad-hoc pattern as `session_visible_to_caller` in §1). See §5 below for the full storage investigation this triggered. Its role-casing bug was confirmed real and permanent, not just suspected: `select ... from auth.users where raw_app_meta_data ? 'role'` returned **zero rows** — nothing has ever populated `app_metadata.role`, so `is_supervisor()` always evaluated `false` for every user, including real Supervisors, for its entire existence. Once the two dependent storage policies were themselves confirmed unnecessary (§5) and dropped, `is_supervisor()` was dropped cleanly (`drop function if exists public.is_supervisor();`).

**Lesson carried forward from this:** a repo grep for "is this used anywhere" is not sufficient when Postgres objects (functions, policies, including storage policies) can be created directly via the SQL editor / dashboard with no corresponding file in the repo — this is now the fourth time this session that pattern caused a doc or an assumption to be wrong (`session_visible_to_caller`/`delivery_request_visible_to_caller` in §1, `maintenance_records`'s missing `DATABASE.md` section, and now this). `DROP ... CASCADE` was correctly avoided in favor of investigating each dependent object first.

## 2. `SECURITY DEFINER` functions publicly executable via RPC

Flagged: `current_user_role`, `is_admin`, `enforce_role_change_admin_only`, `enforce_supervisor_status_only_update`, `rls_auto_enable`, `delivery_request_visible_to_caller`, `session_visible_to_caller` — all callable by both `anon` and `authenticated` via `/rest/v1/rpc/<name>`.

**Assessment:** for `current_user_role`, `is_admin`, `delivery_request_visible_to_caller`, and `session_visible_to_caller`, this is very likely intentional and low-risk — they're read-only predicate functions designed to be called from RLS policies (`SUPABASE_GOTCHAS.md` gotchas #5 and #9), and calling them directly via RPC only returns a boolean/role string, not any row data. `enforce_role_change_admin_only` and `enforce_supervisor_status_only_update` are trigger functions (`SUPABASE_GOTCHAS.md` gotcha #5's `enforce_role_change_admin_only` example) — Postgres allows calling a trigger function directly via RPC, but doing so outside a trigger context is generally a no-op or error, not a bypass; this should be confirmed rather than assumed.

**`rls_auto_enable` — resolved, read directly via `pg_get_functiondef` 2026-08-30.** It's an event-trigger function (`returns event_trigger`) that fires on `CREATE TABLE`/`CREATE TABLE AS`/`SELECT INTO` in `public` and automatically runs `alter table ... enable row level security` on the new table — a safety net against a newly created table silently having no RLS at all (the exact class of gap gotcha #8 documents happening to `driver_records` and friends at creation time). Legitimate infra, not a mystery function. Its `search_path=pg_catalog` (not `public`) is correct for what it does — it only reads `pg_event_trigger_ddl_commands()`, a system catalog function, never touches `public` schema tables directly. RPC exposure to `authenticated` is harmless: calling it manually outside actual DDL-event-trigger context does nothing (the function body only has meaning inside the `FOR cmd IN SELECT * FROM pg_event_trigger_ddl_commands()` loop, which is empty outside a real trigger firing).

## 3. RLS policies with `USING (true)` / `WITH CHECK (true)`

**Resolved 2026-08-30** (`20260830120000_harden_permissive_rls_policies.sql`, `20260830130000_harden_driver_default_assignments.sql`) — before fixing anything, each table's live grants were checked directly (`information_schema.role_table_grants`), not assumed from the Advisor export, since the `alerts` investigation below (§3's `anon`/`sessions` note) had already shown the Advisor and the docs can each be stale in either direction:

- **`alerts`** — the `anon insert alerts` policy the Advisor still listed was confirmed **dead**: `anon` has zero grants on the table (`DATABASE.md`'s claim that this was revoked 2026-08-12 turned out to be the accurate one; `STATUS.md` and the Advisor were the stale ones). The two dead `anon` policies (`anon insert alerts`, `anon select alerts`) were dropped as cleanup — no behavior change, since they were already unreachable.
- **`sessions`** — same result: `authenticated` only ever had `SELECT` (no `INSERT`/`UPDATE`), and `anon` had nothing at all, so `anon insert/select/update sessions` were confirmed dead and dropped as cleanup. The two real policies (`Admins and Supervisors can read sessions`, `assigned crew can read own sessions`) were untouched and are the ones actually gating access.
- **`maintenance_records` / `trucks`** — confirmed **live**: `authenticated` held real `INSERT`/`UPDATE`/`DELETE` grants on both, combined with the `USING(true)`/`WITH CHECK(true)` policies, meaning any logged-in Driver/Helper/Customer (not just Admin/Supervisor) could write or delete rows via direct REST calls. Fixed by replacing the four permissive write policies on each table with a single `for all to authenticated using/with check (current_user_role() = ANY (ARRAY['Admin','Supervisor']))` policy, matching the precedent already established by `quotation_settings` (`20260826100000_quotation_settings.sql`). The public `SELECT` policies on both tables were left untouched (never confirmed as a problem). Verified live post-fix via curl: an authenticated Driver token's `PATCH /rest/v1/trucks` now returns `200` with an empty body (RLS silently filters the row) and no change persists; Supervisor/Admin writes through the real UI (`AddTruckModal`, `SupTruckProfile`/`AdminTruckProfile`) still work.
- **`driver_records`** — the two `INSERT`/insert-adjacent findings (`Allow authenticated inserts to driver_records`, `public insert driver_records`) were confirmed **dead**: `authenticated` had no `INSERT`/`UPDATE`/`DELETE` grant on this table at all, only `SELECT`. But that `SELECT` grant made `Allow public read driver_records` (`qual: true`) **live** — any logged-in user of any role could read every driver's name fields, contradicting the `service_role`-only design gotcha #8 documented for the `*_records` tables. Fixed by dropping all five pre-existing policies (the two dead inserts, the two `is_supervisor()`-scoped-but-oddly-`anon`-roled ones, and the unrestricted read) and replacing with `admins and supervisors read driver_records` (SELECT) + `admins and supervisors manage driver_records` (ALL), both gated on `current_user_role()`, same pattern as above.
- **`driver_default_assignments`** — confirmed **live**: its own migration (`20260826110000_driver_default_assignments.sql`) explicitly copied "the same open-to-authenticated model as the trucks table," and `authenticated` did hold full `SELECT`/`INSERT`/`UPDATE`/`DELETE`. Verified exploitable pre-fix via curl (an authenticated Driver token's `POST /rest/v1/driver_default_assignments` succeeded, `201`, row created and then manually cleaned up) and verified fixed post-fix (same request now returns `403`, Postgres code `42501`, no row created). Fixed with the same `current_user_role()`-gated `for all` policy.

The `search_path` question in §1 remains open — none of the fixes above touched `current_user_role()`'s definition or any other function, only table policies.

Flagged, by table:

- `alerts` — `anon insert alerts` (INSERT, `anon`)
- `sessions` — `anon insert sessions` (INSERT, `anon`), `anon update sessions` (UPDATE, `anon`)
- `driver_records` — `Allow authenticated inserts to driver_records` (INSERT, `authenticated`), `public insert driver_records` (INSERT, role `-`/public)
- `driver_default_assignments` — `authenticated can manage driver default assignments` (ALL, `authenticated`)
- `maintenance_records` — insert/update/delete, role `-`/public, all three
- `trucks` — insert/update/delete, role `-`/public, all three

**`alerts` / `sessions` anon insert+update — likely intentional, matches documented Pi auth model.** `00_IMPLEMENTATION_RULES.md` and `05_GPS_PIPELINE.md`/`06_DROWSINESS_ALERT_PIPELINE.md` establish that the Raspberry Pi authenticates itself with `device_secret` (hashed server-side, `SUPABASE_GOTCHAS.md` gotcha's device-auth note) inside `alert-upload`/`gps-upload`/`device-heartbeat`, all of which use `service_role` internally (confirmed against `supabase/functions/*/index.ts`, all five Edge Functions create a `service_role` client) — meaning `service_role` bypasses these RLS policies entirely and doesn't need them. That raises the real question this doc can't answer by reading code alone: **why do `anon`-permissive policies exist on `alerts`/`sessions` at all, if every legitimate write path already goes through a `service_role` Edge Function?** If nothing legitimate ever inserts into `alerts` or `sessions` as `anon` directly via REST, these policies mean anyone holding the public anon key (shipped in the deployed JS bundle, per `scripts/README.md`'s own note about `admin-users`) can `POST /rest/v1/alerts` or `/rest/v1/sessions` directly — forging drowsiness alerts or session rows, or overwriting `sessions.driver_id`/`session_status` via the `anon update sessions` policy — without going through `device_secret` auth at all. This is structurally the same shape as `SUPABASE_GOTCHAS.md` gotcha #6 (a permissive `public`/`anon` policy meant for one narrow legitimate case turning into an open write). Needs a decision, not a silent fix, since there may be a legitimate anon-write path (e.g. an unauthenticated device flow) this document doesn't have visibility into.

**`driver_records` — two overlapping insert policies, one of them `public`.** `driver_records` is one of the five `*_records` tables gotcha #8 specifically called out as designed to be `service_role`-only, reachable only through `admin-users` (`DATABASE.md`, `AUTHENTICATION.md`). A `public insert driver_records` policy with `with_check: true` directly contradicts that design intent — it would let anyone with the anon key `POST /rest/v1/driver_records` and create arbitrary driver-record rows (name, license info, etc. per gotcha #8's description of what these tables hold), bypassing `admin-users` entirely. This looks like the same class of bug as gotcha #6's original `users` table issue, on a different table gotcha #8 already flagged as sensitive. **Recommend treating as a real bug**, but confirm first whether `Allow authenticated inserts to driver_records` (the `authenticated`-scoped duplicate) is the one actually in use and the `public` one is leftover/dead, since two insert policies on the same table for the same command is itself worth explaining before removing either.

**`maintenance_records` / `trucks` — insert/update/delete open to role `-` (public/unscoped).** Both tables are written from Admin/Supervisor-only screens (`SupTrucks.jsx`, `AdminTrucks.jsx`, `AdminTruckProfile.jsx`, `SupTruckProfile.jsx`, `AddTruckModal.jsx`, `EditDeviceModal.jsx`, `RegisterDeviceModal.jsx` — confirmed via search, all under `src/pages`/`src/components`, none of them Driver/Helper/Customer-facing). Nothing in `01_SYSTEM_ARCHITECTURE.md`, `PROJECT_CONSTRAINTS.md`, or `72928ee`/`f8ad278`'s Truck Module work (per recent commit history) documents an intentional reason for an unauthenticated or cross-role write path into either table. If these policies mean literally any anon-key holder can create/edit/delete trucks and maintenance history with no login, that's the most severe finding in this set — worse than `driver_records`, since maintenance/truck integrity is operationally load-bearing (dispatch, PMS scheduling per `c53d6cd`'s "PMS and Maintenance Tab Updates" commit) and there's no `admin-users`-style server-side gate to fall back on the way `*_records` tables have. **Needs a decision and, most likely, a fix scoping both to `authenticated` + an `is_admin()`/`is_supervisor()` check**, matching the pattern already established for `users` role-gating (`SUPABASE_GOTCHAS.md` gotcha #5/#6).

**`driver_default_assignments` — `ALL` for `authenticated`, `USING (true)`.** No per-row scoping at all for any authenticated user (Driver/Helper/Customer included, not just Admin/Supervisor) to read/write/delete every row. Not documented anywhere found in `IMPLEMENTATION/`. Needs a decision on intended scope — likely should be Admin/Supervisor-only, same shape as the trucks/maintenance finding above, but this document isn't certain what "driver default assignment" covers without more context.

## 5. `storage.objects` policies on `driver-profile-pics` — not in the original Advisor export, found while investigating `is_supervisor()`

The Supabase Advisor's security lint (this doc's original §1-4) does not cover `storage.objects` RLS policies at all — this was found only because dropping `is_supervisor()` failed on a dependency error. **Resolved 2026-08-30** (ad hoc SQL, no migration file — see note below):

- **`Allow anon uploads to driver-profile-pics`** (`INSERT`, role `anon`, `with_check: bucket_id = 'driver-profile-pics'`, no owner/path restriction) — the most severe finding in this entire audit. `driver-profile-pics` is a `public: true` bucket (`storage.buckets`, confirmed live), so this combination meant **any unauthenticated request** could upload an arbitrary file to a publicly-served URL, no login required at all — unlike every other finding in this document, which at minimum required a valid `authenticated` session.
- **`Allow authenticated uploads to driver-profile-pics`** (`INSERT`, role `authenticated`, same unrestricted `with_check`) — one tier less severe: any logged-in user (not just Admin/Supervisor) could upload to any filename, including overwriting another user's `{auth_id}.jpg`.
- **`Supervisors can update/delete driver profile pictures`** — gated on `is_supervisor()`, which (per §1) always evaluated `false`. Non-functional for their entire existence.

Verified via `storage.objects` contents (not just the policy text) before touching anything: two of the three existing files (`owner: null`, flat `{uuid}.jpg` names) matched the legitimate upload path; one (`owner` set, `{folder}/{timestamp}-{uuid}.jpg` naming, dated 2026-05-31 — five days after the bucket's 2026-05-26 creation, long before this project's current `admin-users`-only design) was uploaded by a real authenticated client directly, not through the Edge Function — evidence the `authenticated` policy was used at some point (an early prototype/onboarding flow, most likely), though not evidence of malicious abuse. No sign the `anon` policy was ever actually exploited, but that's a "nobody's found it yet" observation, not a safety property.

Confirmed safe to close entirely (not narrow — remove) by reading `admin-users/index.ts` directly: both `upload-profile-picture` (line ~1565, `adminClient.storage.from(...).upload(...)`) and `remove-profile-picture` (line ~1613, `adminClient.storage.from(...).remove(...)`) exclusively use the `service_role`-backed `adminClient`, which bypasses `storage.objects` RLS entirely — confirmed via a repo-wide grep that no page, component, other Edge Function, or script anywhere calls `.storage.from()` for this bucket. All four policies dropped:
```sql
drop policy if exists "Allow anon uploads to driver-profile-pics" on storage.objects;
drop policy if exists "Allow authenticated uploads to driver-profile-pics" on storage.objects;
drop policy if exists "Supervisors can update driver profile pictures" on storage.objects;
drop policy if exists "Supervisors can delete driver profile pictures" on storage.objects;
```
Verified post-fix via curl with a Driver access token attempting a raw `POST` to `/storage/v1/object/driver-profile-pics/hack-test.txt`: now `400`/`403`, "new row violates row-level security policy." Verified the legitimate path still works via manual UI test (Profile page picture upload, any role). Full-repo `npm run build` (clean) and a dependency check across every Edge Function referencing `trucks`/`maintenance_records`/`driver_default_assignments`/`driver_records` (`admin-users`, `driver-trip` — both exclusively `service_role`) confirmed nothing else in the app was affected by any of this session's policy changes.

`driver-profile-pics` now has zero `anon`/`authenticated` policies on `storage.objects` — matching the `service_role`-only pattern already established for the `*_records` tables (gotcha #8) and `crew_availability`. Public read access is unaffected (that's the bucket's own `public: true` flag, a separate mechanism from RLS policies).
