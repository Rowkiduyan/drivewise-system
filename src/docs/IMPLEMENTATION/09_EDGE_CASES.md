# Phase 9 - Edge Cases

Implement handling for:

- Raspberry Pi never powered on
- Driver intentionally never powers on the Raspberry Pi (Trip proceeds; dashboard shows Monitoring Unavailable, not an error)
- Raspberry Pi loses internet
- Device offline during an active Trip
- Monitoring unavailable (Trip started, Raspberry Pi has never connected — see `08_REALTIME_DASHBOARD.md`)
- GPS unavailable
- Camera unavailable
- Duplicate Start Trip
- Driver attempts Start Trip while already on a different Active or Paused Trip (rejected — see `PROJECT_CONSTRAINTS.md`)
- Device already has an Active session
- Device reassignment while a session is Active
- End Trip while Raspberry Pi is Offline
- Overnight pause and resume (Pause Trip, device powered off overnight, Resume Trip the next day — see `03B_PAUSE_AND_RESUME_TRIP.md`)
- Multi-session Trips (a Trip accumulating more than one Session via Pause/Resume)
- Multi-stop Trips (a Trip with more than one planned/delivery stop, still ONE Trip)
- Driver returns to depot and receives a new assignment (a NEW Trip, never a resumption of the completed one — see `01_SYSTEM_ARCHITECTURE.md` and `02_BOOKING_AND_TRIP_CREATION.md`)
- Multiple customer branches within one Trip (still ONE Trip)
- Trip left Paused indefinitely (driver never presses Resume Trip or End Trip) — no automatic expiry, cancellation, or state change; the Trip stays Paused until the driver acts, same as heartbeat loss never ending a trip
- Driver ignores/dismisses the rest stop recommendation (see `03_START_TRIP_AND_SESSION.md`) — purely advisory, never forces a Pause or otherwise changes Trip/Session state

Never infer trip completion from heartbeat loss.

Trips only end when the driver presses End Trip.

A Trip does not automatically end because monitoring/telemetry is unavailable.

## Pre-work status check (done 2026-08-12, nothing implemented yet)

Per `00_IMPLEMENTATION_RULES.md`'s "verify before implementing" process — before writing any Phase 9 code, every bullet above was checked against what Phases 1-8 already built, so this phase doesn't re-derive things that already work or, worse, assume something is handled when it isn't. Three real gaps were found; everything else already works by construction of the existing Trip/Session/heartbeat model. **Start Phase 9 at the "Concrete gaps" list below — the rest of this section is confirmation, not a to-do list.**

### Already handled (verified against code/STATUS.md, not just assumed)

- **Raspberry Pi never powered on / loses internet / device offline during an Active Trip / "Monitoring Unavailable"** — all four are the same mechanism: `devices.last_ping` simply never advances (or stops advancing), and `SupDashboard.jsx`'s `resolveOpsState` (Phase 8) already computes Waiting for Device → Monitoring Unavailable, or Online → Offline, purely from that. No Edge Function (`driver-trip`/`device-heartbeat`/`gps-upload`/`alert-upload`) has any code path that reacts to a missed heartbeat by touching Trip/Session state. The Online→Offline and never-connected→Monitoring-Unavailable transitions were click-tested live during Phase 8 (`STATUS.md`'s Phase 8 entry); the mid-trip "was Online, loses internet, goes Offline" variant specifically wasn't isolated as its own test, but is the identical code path.
- **Duplicate Start Trip / Device already has an Active session** — both enforced today: driver-scoped check + `sessions_one_active_per_device` unique index for Start Trip (curl-tested per `STATUS.md`, `DR-0011`/`DR-0016`, both returned `409`); a symmetric pre-check + the same DB constraint for Resume Trip (code present, but per `STATUS.md` "not separately tested... deemed low-risk" — worth an actual curl/click test in this phase rather than continuing to assume).
- **End Trip while the Pi is Offline** — `end-trip` never reads device state at all; `07_END_TRIP.md` documents shutting down the Pi as something that happens *after* End Trip. Structurally guaranteed, not separately tested against an actually-Offline device.
- **Overnight pause and resume** — `resume-trip` has no time-based expiry anywhere; a Resume 12 hours or 12 seconds after Pause is identical code. Documented explicitly in `03B_PAUSE_AND_RESUME_TRIP.md`. Pause/Resume itself is click-tested; the specific multi-hour gap between the two calls has never been exercised (nothing in the code would care, but that's inference, not verification).
- **Multi-session Trips** — the core Pause/Resume design; `SupDashboard.jsx`'s Phase 8 logic already reasons over multiple closed Sessions per delivery correctly. Click-tested via repeated Pause/Resume cycles (`STATUS.md`).
- **Driver returns to depot, gets a new assignment later** — structural, not logic that could have a bug here: a new assignment is a new `delivery_requests` row with its own `id`; nothing in the schema links two deliveries together. `07_END_TRIP.md` confirms a Completed trip can't be resumed.
- **Trip left Paused indefinitely** — no code auto-expires or cancels a Paused delivery; the only real-world instance of this (`D002`/`DR-0015` sitting open ~64 hours, `STATUS.md`) turned out to be a UI *discoverability* bug (the stale delivery didn't render as Active so the driver had no way to act on it), not an auto-expiry bug — and that UI bug is already fixed (`STATUS.md`'s "stale-open-session" entry).

### Not yet built, but out of Phase 9's actual reach right now

- **Multi-stop Trips / multiple customer branches within one Trip** — both depend on the `stops` column, which still doesn't exist (`DATABASE.md`'s `delivery_requests` entry, `02_BOOKING_AND_TRIP_CREATION.md`'s Required Schema gap #2). The "still ONE Trip" invariant these bullets care about is trivially true today only because there's no multi-stop Trip yet to accidentally split into two. Phase 9 can confirm the Session/Trip model has no dependency on stop count (it doesn't — verified, `sessions` only ever references `delivery_request_id`), but can't be tested against real multi-stop data until that column and its UI exist.
- **Driver dismisses the rest-stop recommendation** — true as of this pre-work check (2026-08-12); **stale as of 2026-09-03** — the feature was since built (`12_REST_STOP_RECOMMENDATIONS.md`, 2026-08-13/14, `DriverDeliveries.jsx`'s `restStopRecommended`/`restStopDismissed` state), so this bullet's premise no longer holds. Dismissing it is already covered by that doc's own design (purely advisory, dismissing clears the banner without touching Trip/Session state, never re-shows itself once dismissed or the Trip ends) — not an open edge case for Phase 9 to pick up.

### Concrete gaps — the actual to-do list for this phase

1. **"Driver attempts Start Trip while already on a different Active *or Paused* Trip" is only half-enforced.** `driver-trip`'s `start-trip` correctly rejects a second Start Trip while the driver has another delivery's session **Active** (driver-scoped, not delivery-scoped — curl-confirmed cross-delivery in `STATUS.md`). It does **not** check for a **Paused** Trip on a different delivery — by definition, "Paused" means no open Active session, which is exactly the state that check can't see. This is self-documented in `driver-trip/index.ts`'s own inline comment near the Start Trip guard, which explicitly hands "full Active-or-Paused enforcement across every delivery" to this phase. Today, a driver with one Paused Trip could Start Trip on a second, unrelated delivery and it would succeed — contradicting `PROJECT_CONSTRAINTS.md`'s "one Active or Paused Trip per driver at a time." This is the clearest, most concrete item to build first.
2. ~~Device reassignment while a session is Active has no guard at all.~~ **Fixed 2026-08-12.** The Admin "Edit Device" UI (`EditDeviceModal.jsx`) wrote a device's `plate_number` directly with zero check for whether that device currently has an Active session, silently violating `PROJECT_CONSTRAINTS.md`'s "one active device assignment per truck" rule. The target-truck-already-has-a-device case was already prevented separately (the plate dropdown only ever offers trucks with no device assigned, plus the device's own current plate). Decision made: **block outright**, not warn-and-allow — `performUpdate` now queries `sessions` for an Active row on `device_id` before any reassignment away from the device's current plate, and rejects with "This device is powering an active trip — end or pause the trip before reassigning it." if one exists. This also sidesteps a second, previously-unflagged consequence: `08_REALTIME_DASHBOARD.md`'s Supervisor Dashboard resolves Device/Trip state per truck via a live `devices.plate_number` join — a live reassignment away from a truck with an Active session would have made that truck's dashboard entry read "no device"/Waiting-for-Device even though the original Pi was still actively reporting telemetry against its still-open session. Blocking reassignment outright while Active makes that display-corruption scenario unreachable, not just the write-time constraint violation. **Click-tested live 2026-08-12**: created a real Active session via `driver-trip`'s `start-trip` (`DR-0011`/`D002`, device `DV-1114`, disposable fixture — `DR-0011` reset from `DELIVERED` to `ASSIGNED` beforehand, reverted to `DELIVERED` via `end-trip` afterward, session closed `Completed`), then attempted to reassign `DV-1114` to a different truck via `EditDeviceModal.jsx` in the browser — confirmed rejected with the expected error message.
3. ~~Camera-unavailable failure mode isn't isolated on the Pi side.~~ **Fixed 2026-08-14.** `pi/drowsiness_monitor.py`'s `Picamera2()` init (previously no try/except, before the heartbeat/GPS threads even started) is now wrapped in a try/except that sets `camera_available = False` and logs the error instead of crashing the process; the heartbeat/GPS/alert threads are started unconditionally right after, regardless of camera outcome. The main loop's per-frame detection block now checks `camera_available` (after the existing Paused-session check) and, when False, sleeps and skips detection entirely rather than calling `picam2.capture_array()` on a `None`/unstarted camera. Not yet re-tested on physical hardware against a forced camera fault (the 2026-08-13 crash-loop that surfaced this gap was reproduced via a real wiring fault, not something reliably re-triggerable on demand) — build-verified only (`python -m py_compile`).

### Progress (2026-08-12)

**Gap #1 (Paused-trip Start Trip guard) built, deployed, and verified working.** `driver-trip`'s `start-trip` action now also rejects when the driver has a *different* delivery sitting Paused (past `ASSIGNED`, no open Active session), not just an Active one — `409`, "You already have a paused trip in progress — resume or end it before starting a new one." Deployed via `npx supabase functions deploy driver-trip`.

**Found while building it, fixed 2026-08-12 — a real stuck-state gap in `DriverDeliveries.jsx`'s "Start Pickup" flow.** That button called `update-driver-delivery` (advances `delivery_requests.status` to `OUT_FOR_PICKUP`) *before* calling `start-trip`. If `start-trip` then rejected for any reason — including gap #1's new guard, which triggers far more often than the pre-existing device-conflict case it originally guarded against — the delivery was left showing `OUT_FOR_PICKUP` with no Session behind it at all, the same stuck-delivery shape as the `D002`/`DR-0015` incident (`STATUS.md`), except reachable on a normal, expected rejection instead of a rare fluke. **Fixed by reordering `advanceStage`'s `FOR_PICKUP` branch (`DriverDeliveries.jsx`): `start-trip` is now called first, while `delivery_requests.status` is still `ASSIGNED` (which `start-trip` already accepts), and `update-driver-delivery` only runs after it succeeds** — so status is never advanced without a genuine Session behind it. The `DELIVERED` branch (`end-trip` after the status update) was left in its original order; that path isn't the guardrail-heavy one this gap was about. A small residual, accepted rather than engineered around: if `update-driver-delivery` itself fails *after* `start-trip` already succeeded, the Session is genuinely Active but the displayed stage label lags one step — recoverable by retrying Start Pickup, and a plain status-write failure (rare) rather than a guardrail rejection (common), so not the stuck-dead-end this fix targets. The one thing that was already fixed alongside gap #1: `start-trip`'s failure handler previously showed a generic "please try again" alert for every rejection reason, which is actively misleading for a guardrail rejection (retrying does nothing) — it now surfaces the Edge Function's real error message instead.

### Also noticed, not a Phase 9 item

`driver-trip/index.ts`'s file header comment ("End Trip is not implemented yet") — fixed 2026-08-12 alongside gap #1, since the file was already being touched.

**Found 2026-09-08, parked — not yet fixed. A never-started `ASSIGNED` delivery whose `pickupDate` has passed can never become reachable again.** `workspaceDelivery`'s three selection tiers (`DriverDeliveries.jsx`'s `loadDeliveries`) are: an open Session, a Paused trip (`FOR_PICKUP`/`OUT_FOR_DELIVERY` with no open Session, date-independent by design — see the 2026-09-08 STATUS.md entry), or `pickupDate === today` as the last resort for a delivery still sitting at `ASSIGNED`. That third tier is an exact-date match, not `<=` — so once a day passes with the driver never clicking "Start Pickup," the delivery matches none of the three tiers and falls into History's **"Not Started"** section (relabeled from "Overdue" 2026-09-08 — same section/same `data.overdue`/`filteredOverdue` internally, just a clearer display name since the badge/heading was being confused with a late-but-in-progress trip). Unlike a Paused trip, there is no way back: `DeliveryDetailView` (what opens when clicking any History row) is entirely read-only — confirmed no `onResume`/`onStageAdvance`/`pauseTrip`/`resumeTrip` wiring anywhere in it — and "Start Pickup" only ever renders inside the one pinned Today workspace card. Live example in real data: `DR-0053` (`D002`, `ASSIGNED`, `pickup_date` 2026-09-05, no session) sits in History → Not Started with no path to ever start it.

- **Recommended fix (not yet implemented, user wants to tackle later):** widen the third tier from `pickupDate === today` to `pickupDate <= today`. Since `nonTerminal` is already sorted ascending by `pickupDate`, `.find()` would naturally surface the *oldest* overdue-and-unstarted delivery first — the most urgent one — while today's own delivery (if a different one) simply renders under "Also today" as it already does.
- **Known tradeoff of that fix:** only one delivery can occupy the workspace slot at a time (the existing single-workspace invariant, backed by `driver-trip`'s "one Active-or-Paused trip per driver" guard) — if a driver has *multiple* stale `ASSIGNED` deliveries, only the oldest gets pinned to Today per load; the rest stay stuck in Not Started until that one is resolved. Strictly better than today (currently none are ever reachable), but not a full fix for that multi-stale-delivery case.
- Same gap likely applies to `HelperDeliveries.jsx`'s mirrored port — not separately confirmed.

**Discussed 2026-09-08, parked — not yet implemented: allow a driver to start a new trip while a different trip sits Paused, if it's on a different truck.** Today, `start-trip`'s `otherInProgress` guard blocks on *any* other paused delivery for this driver, regardless of truck — a driver who paused a trip in Truck A overnight can't start an unrelated trip in Truck B the next morning without first resuming-then-re-pausing (or ending) Truck A's trip, even though the two trucks/devices don't actually conflict.

- **Proposed backend fix:** narrow `otherInProgress`'s query to also filter `.eq("assigned_truck_plate", delivery.assigned_truck_plate)` — only block when the *other* paused delivery shares the same truck (the real conflict: one truck's Pi/`device_id` can't back two "current" sessions at once). The separate `existingActive` check (any Active session, any truck) stays as-is — a driver can only physically be driving one truck at a time, so that one should remain driver-scoped, not truck-scoped. This half is low-risk and could ship on its own.
- **Frontend implication, NOT small:** `workspaceDelivery` is a single object today, picked by `.find()` — first match wins. If a driver ends up with an Active session on Truck B and a Paused one on Truck A at the same time, the current logic would silently hide Truck A's paused trip again (the same class of bug the 2026-09-08 paused-tier fix solved for staleness, reintroduced here for concurrency). A real fix needs `workspaceDelivery` to become a short list (one live card per truck), with every live-session `useEffect` in `DriverDeliveries.jsx` (GPS, alerts, phone-GPS broadcast, rest-stop accumulator) keyed per-delivery instead of off one shared closure — a genuine restructure of the file's most sensitive section, not a quick add.
- **Recommendation given to the user:** ship the backend half only if/when it's actually useful; don't take on the frontend restructure unless multi-truck-per-driver dispatch is a real operational scenario, since it's a lot of surface area for a possibly-rare case.
